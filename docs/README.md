# docs/

> Mosaic 的文档目录。本文说清每个子目录的读者、职责边界，以及一份新文档该放哪里。
> 三份根目录文档不在这里：`README.md` 面向插件用户（英文），`AGENTS.md` 面向 AI agent 的开发规程，`CLAUDE.md` 只是 `AGENTS.md` 的 import stub。

## 目录职责

| 目录 | 读者 | 放什么 | 不放什么 |
| --- | --- | --- | --- |
| `guides/` | 使用者 | **how**：各内容块的写法、属性表、payload 契约、报错清单；`publishing-to-obsidian.md` 是发版操作步骤 | 设计理由（那是 `design/`）、代码实现 |
| `design/` | 贡献者与 agent | **why**：每个区块为什么这么设计，机制取舍与被否决的方案 | 属性明细、用法示例、代码 |
| `policies/` | 发版前逐条对照 | Obsidian **官方规范原文**归档，带 source url 与抓取日期，文件名统一 `obsidian-` 前缀 | Mosaic 自己的规则（那在 `AGENTS.md`） |
| `research/` | 迭代前的技术决策 | 第三方技术调研档案：候选方案的能力边界、许可证、维护状态、实测数据 | 调研结论落地后的实施细节 |
| `_assets/` | 被文档引用 | 文档截图，dark 主题实拍，内容一律用模拟英文假数据 | 与文档无关的图片 |

`mosaic-intro.md`（英文为准）与 `mosaic-intro-zh.md`（镜像翻译）讲定位、内容块全景与 Roadmap，是新读者的入口。

## 一份新文档放哪里

按「读者是谁」判断，一步到位：

1. 使用者要照着做 → `guides/`
2. 改代码的人需要知道当初为什么这么定 → `design/`
3. 是别人（Obsidian 官方）定的规矩，我们只负责遵守 → `policies/`
4. 是「该不该换、该选哪个」的调研，结论尚未落地 → `research/`
5. 以上都不是 → **多半不该进这个仓库**，见下。

同一件事在两个目录各有一份是常态：`guides/chart.md` 讲怎么写属性，`design/chart.md` 讲这些属性为什么长这样。两边都写全，不要互相塞。

## 不进 docs 的东西

这个仓库是公开的，以下几类一律不写进任何文档：

- **工作过程记录**——已完成的实施计划、任务清单、进度归档。它们的价值在完成的那一刻就兑现了，留在公开仓库只是持续暴露内部工作方式。
- **本机环境**——绝对路径、用户名、私有工具链、个人 vault 位置。要举例就用环境变量名或泛化描述。
- **个人与公司信息**——真实业务线名称、内部仓库名、私有项目名、真实业务数据。示例数据一律现编。
- **其他项目的源码路径与行号**——除非那是公开可查的第三方开源库（`research/` 里对 AntV / ECharts 源码的引用属于此列）。
- **构建产物**——`main.js` 不进 git，分发走 GitHub Releases。
